# Agent Note: 迁移到 DSH 0.2.x 协议

Status: implemented — 客户端、内置插件与发布验证已迁移到 DSH 0.2.1-rc.2

## Problem

本地 npm latest 是 `@deepseek-ai/dsh@0.2.1-rc.2`，仓库钉在 `0.1.1-rc.2`。0.2.x 带来用户明确要的官方对齐能力（`deepseek-flash` 目录、v41 图片 token 计费、`compaction-image-offload`、按模型的 prompt/tool cache 标记），看起来只是"升个版本"。实测（在 `dist/.dsh-runtime-cache/0.2.1-rc.2` 的纯净运行时上起 Host 验证）它不是：

1. **鉴权变成必需**。启动行从 `dsh web: http://127.0.0.1:<port>` 变成带 token 的 `...?token=...`；`GET /?token=X` 返回 303 并下发 `Set-Cookie: dsh-auth-...`（HttpOnly / SameSite=Strict）。没有这个 cookie，`POST /api/*` 全部 401。原生客户端当前直接 RPC，不认 token。
2. **legacy RPC 表面整体消失**。客户端用到的 41 个点号方法（`host.describe`、`session.list`、`session.prompt`、`workspace.*`、`settings.*`、`credentials.*`、`llm.*`、`subagent.*`、`agentPreset.*`、`skill.list`、`goal.*`）在 0.2.1-rc.2 上全部返回 **HTTP 404 not found**。取而代之的是 `@deepseek-ai/dsh-api-*-controller` 一族（session / workspace / settings / job / account / terminal）用 typert `Remote()` 注册的两段式方法（如 `session/list`、`session/modelCatalog`、`workspace/create`），外加 `dsh-api-gateway`。`dsh-host-apiproxy` 与 `dsh-agent-presets` 这两个包已经不存在（后者拆成 `dsh-agent-preset` + `dsh-agent-preset-registry`）。
3. **运行时补丁的第一处锚点就失效**，且不是锚点写错：subagent 的可续跑 API 被重构成 provider/activation 模型——`ContinuableStartSpec` → `ContinuableCreateSpec`、`startContinuable` → `SubagentActivationSpec` + `startActivation` / `startLocal` / `startExternal`、`drainContinuableChildren` 与 `freezeMessage` 消失。好消息是上游把我们要的几项收编了：`SubagentStartRequest` 原生带 `cwd` / `agentPreset` / `label`，`childSessionMeta(parent, childDepth, isSeeded, selectedPreset?)` 原生支持 preset。
4. **自研插件包要跟着改**：`macos/Runtime-extras/dsh-agent-platform` 有 2 处直接调用被重构的 API（`index.js` 的 `ctx.subagents.startContinuable(...)`、`lifecycle.js` 的 `subagents.drainContinuableChildren(...)`），三个 extras 包的 peerDependencies 全部钉死 `0.1.1-rc.2`。

5. **存量数据不兼容**：`SESSION_FORMAT_VERSION` 从 0 变成 4（新 header 明确不接受 seedLength 字段），`SUBAGENT_DESCRIPTOR_VERSION` 从 2 变成 3。用户已有的会话日志与 Agent Platform 的子会话描述符在新 runtime 上需要一条明确的迁移/兼容路径，否则升级即"历史会话打不开、批次上下文无法恢复"。
6. **上游同时删掉了我们补丁的几项能力**（逐条对照见下）：messageId 幂等、子会话 sandboxMode 覆盖、受管子会话 follow-up 守卫在 0.2.1 都没有等价物；冷恢复还原 `maxTokens` 则是上游明确的设计拒绝（per-activation knobs 故意不进 descriptor）。反过来 cwd / agentPreset / 预约 childId 已被上游收编（`SubagentStartRequest.cwd`、`SubagentStartRequest.agentPreset`、`SubagentActivationSpec.childId` + `DUPLICATE_CHILD` 校验），这几处补丁可以直接删。`agent-platform/batches` 事件类型仍然必须注册——0.2.1 的下游插件事件规范前缀是 `plugin:`，但存量日志里已经有旧类型名的事件，读取路径不接受未注册类型。

结论：0.2.x 不是版本号 bump，而是"换协议 + 迁补丁 + 迁插件 + 迁存量数据"的客户端迁移项目。

### 实测补充（P1 只读冒烟已完成）

在**真实存量会话库的副本**上起 0.2.1-rc.2 Host 跑过（会话目录共 128 个 `session.jsonl.zstd`、18MB，复制到临时 home，原库只读未受影响）：

- **会话能列全**：`session/list`（gateway 形状 `{args:{_request:{}}}`）返回 **128 条**，字段为 `sessionId / updatedAt / agentAvailable / formatStatus / running / blank / cwd`。
- **但格式全部是 `migration-required`**：128/128，`agentAvailable` 全为 false；`session/projections` 返回 `{kind:"migration-required", values:{}}`。客户端 0.2 版必须有显式的"迁移中"呈现，不能假装能读。
- **迁移由"打开/派发"触发，不是启动时自动跑**：`session/projections` 对 `migration-required` 直接短路返回；只有把会话真正 attach（走 `session/prompt`，参数 `{request:{requestId,sessionId,mode,content}}`，`requestId` 是必填的 client-minted id）之后，`session/list` 的 `formatStatus` 才翻成 `current`，`projections` 变成 `kind:"sequenced"` 并带出真实 `title`（实测 `migration-required` → `current`，标题读到了）。
- **迁移链完整**：包内有 `dsh-session-format-v0-to-v1` … `v3-to-v4` 四级 catalog，v0 的 header（含我们补丁写入的 `seedLength`）能被接受并升级，冒烟期间没有任何 migration 报错。
- **结论修正**：原先担心的"历史会话直接打不开"不成立——**能读，但需要一次 attach 触发的迁移**。客户端要做的不是迁移工具，而是：(a) 把 `migration-required` 当作一等状态展示（旧会话可点，点开提示"正在升级此会话"）；(b) 迁移是**写操作**（会改写磁盘会话文件），首次升级必须让用户知情；(c) 迁移后的会话对 0.1.1 旧客户端可能不再可读，升级前应提供备份或只读导出。
- **gateway 调用形状**（实测）：payload 必须是 `{args:{...}}`；多数端点参数名是 `request`（`session/prompt`、`session/projections`、`session/attachment`），`session/list` 却是 `_request`。原客户端那 41 个点号方法在 0.2.1 上仍全部 404。

### 0.2.1 传输契约（已从产物源码逐条确认）

迁移的 Swift 侧只需实现下面三件事，全部以 `dist/.dsh-runtime-cache/0.2.1-rc.2` 里的产物为证据：

**1) 启动与鉴权**

- 启动行：`dsh web: http://127.0.0.1:<port>/?token=<token>`（0.1.1 没有 token 段）。
- `GET <该 URL>`（不要跟随重定向）→ `303` + `Set-Cookie: dsh-auth-<id>=v1.<payload>.<sig>; Max-Age=2592000; HttpOnly; SameSite=Strict`。
- 之后所有 `POST /api/*` 与 WebSocket 升级都必须带这条 cookie，否则 401。
- 证据：`dsh-host-webserver/lib/index.js`（`text/event-stream` 不被缓冲、upgrade 路由表）、实测 303 + Set-Cookie。

**2) 一元调用（替代 0.1.1 的点号方法）**

```
POST /api/<namespace>/<method>
Content-Type: application/json
Cookie: dsh-auth-...=...
{ "type": "client-request", "rpcId": "<uuid>", "method": "<namespace>/<method>", "payload": { "args": { ... } } }
```

响应 `{ "type": "server-response", "rpcId": "<同一 uuid>", "result": { "ok": true, "value": ... } | { "ok": false, "error": { code, message, details } } }`。

- payload 必须是 `{args:{...}}`（实测：裸 payload 报 `Remote payload must contain exactly one plain-object args field`）。
- 参数名各端点不同：`session/list` 用 `{args:{_request:{}}}`，`session/prompt` / `session/projections` / `session/attachment` 用 `{args:{request:{...}}}`；形状不符时报 `gateway/arguments-invalid: missing "request"`。
- 证据：`dsh-client-connection/lib/client.node.js`（envelope 构造）、`dsh-api-gateway/lib/index.js`、实测。

**3) 实时事件流（替代 0.1.1 的 `api/events.mux`）**

- 载体：**WebSocket `/api/remote.mux`**（常量 `REMOTE_STREAM_MUX_PATH`），握手带 cookie。
- 帧格式（JSON）：
  - 客户端开流：`{ "type": "open", "streamId": "<uuid>", "endpoint": "<endpoint>", "payload": { "args": {...} } }`
  - 宿主下行：`{ "type": "item", "streamId": ..., "value": ... }`、`{ "type": "end", "streamId": ... }`、`{ "type": "error", "streamId": ..., "error": { code, message, details } }`
  - 客户端上行（双向流）：`{ "type": "item", "streamId", "value" }` / `{ "type": "end", "streamId" }`
  - 取消：`{ "type": "cancel", "streamId" }`
- 应用事件流：以 `endpoint = "$events"`、`payload = { args: {} }` 开一条流。首个 item 必须是 `{ "type": "ready", "clientId": ..., "host": { "home": ... } }`，之后每条事件带 `eventId`；客户端必须为每条事件回一个结果，走一元 RPC `POST /api/$events/result`，`args = { clientId, eventId, outcome: { kind: "next" } | { kind: "result", value? } | { kind: "rejected", error } }`。
- 证据：`dsh-api-gateway/lib/types/stream-protocol.js`（`REMOTE_STREAM_MUX_PATH`、`$events`、`$events/result`、ready 判别）、`dsh-api-gateway/lib/client.node.js:150-340`（`open()` 的 open/item/end/cancel 帧与 `clientId/eventId` 应答循环）。

**Swift 侧落地清单**

1. `DSHHostRuntime`：解析带 token 的启动行 → 握手拿 cookie → 存进 `DSHHostClient`；收 401 时重握手一次并重试。
2. `DSHHostClient.call`：改为 `api/<ns>/<method>` + `payload:{args}` + cookie；方法名表逐个换（见下方功能域）。
3. `DSHEventSocket`：换成一条 `/api/remote.mux` WebSocket + `$events` 逻辑流 + 逐事件 ack；把现有 `applyLiveEvent` 的 switch 从 0.1.1 帧名对齐到 0.2 的 `session/event` 载荷（事件类型名基本沿用：`turn/start`、`assistant/chunk`、`tool/call`、`approval/requested`…，需逐项核对）。

## Decision

实际实现采用一条共享 authenticated transport：

1. `DSHHostRuntime` 严格解析带 token 的启动行，只接受握手 `303`，并用一个拒绝自动跟随重定向的隔离 ephemeral session 取得本次 Host 的 `dsh-auth-*` cookie；unary、Typert、下载和 WebSocket 共用该 cookie，401 重新握手并重放一次。不能再从全局 cookie 存储挑选同名 cookie，否则同时存在多个 loopback Host 时会串到旧端口并导致所有列表/模型请求失败。
2. `DSHHostClient` 统一发送 `{type:"client-request",method,payload:{args}}`，按端点补充 `request` / `_request`，并校验 server response 的 `rpcId`。
3. 一条 `/api/remote.mux` 承载 `$events`、`workspace/follow`、`session/control` 和 root/subagent `session/follow`。新会话在 `session/create` 返回后、首次 prompt 前立即建立 root follow；会话 snapshot 是历史初值，后续 event seq、assistant stream revision 和 chunk index 断裂时 fail closed。
4. 工作区、设置、模型、凭据、技能、目标、审批、提问、子代理和队列分别迁到 0.2 unary/projection/waterfall；审批和问题通过 `$events/result` 按 `clientId + eventId` 逐项结算。
5. 旧会话以 `migration-required` 显示"待升级"；打开前明确提示这是不可逆磁盘格式升级，用户确认后才建立 follow attachment。旧批次 descriptor 不静默伪装恢复。
6. Runtime extras 的 peer dependencies 升到 0.2；Agent Platform 改用 `startActivation`、`sendMessage`、`drainChildren` 和 `session.snapshotEvents()`。运行时补丁仅保留旧 `agent-platform/batches` 事件注册和内置插件挂载。
7. `NativeContractCheck`、单元测试、真实 0.2 Host smoke、构建与签名验证共同覆盖该迁移。

### 已查明的逐项迁移路线（0.2.1 源码对照）

| 能力 | 0.2.1 落点 | 迁移做法 |
|---|---|---|
| 预约 childId | `SubagentActivationSpec.childId` + `assertChildIdAvailable` / `DUPLICATE_CHILD` | 直接换用，删补丁 |
| 子会话 cwd / agentPreset | `SubagentStartRequest.cwd` / `.agentPreset` | 直接换用，删补丁 |
| 精确销毁 | `drainChildren(parent, childIds)`（另有 `activation.dispose()`） | 直接换用；未驻留目标变 no-op（`lifecycle.js` 的早退可删），但 parentSessionId 不一致时旧版静默、新版抛 `UNAUTHORIZED`，会让 `closeContext` 卡在 `closing` |
| messageId 预约 + 幂等 | 无入参位，只有输出位 `SubagentActivation.messageId` | 路线 A：改为把预约 id 写进 `source.rpcId`（上游 user-rpc 同样做法），`dshRunSettlement` 改按 `source.rpcId` 匹配，放宽"返回 id 必须相等"的断言；路线 B：重打补丁（锚点 `submitAdmitted` / `startLocal` / `deliverFollowup` / `coldResume`），补丁面比 0.1.1 更大 |
| 批次快照 sandboxMode | `captureDelegatedPolicyOverrides` 只继承父会话当前 override | 路线 1：补丁里把 `spec.sandboxMode` 合并进 delegatedPolicies（与旧补丁同形，换锚点即可）；路线 2：插件侧用 `sandboxPolicy.setSandboxMode`，但有"是否早于首个受限工具调用"的时序风险（未查证） |
| persona / toolFilter | `SubagentStartRequest` 无此字段；descriptor 只在冷恢复时回填 | 改为每次 run 注册临时 Agent Preset（`agentPresets.register` + `request.agentPreset`），persona 文本与工具白/黑名单映射成 preset 的 plugin 条目（映射细节未查证） |
| 受管子会话 followup 守卫 | 无等价物：`sendMessage` 只校验父子关系，symbol 宿主通道任何同进程插件可用 | 需重新设计（例如在平台侧对 `subagent-settled` 与 turn 结算加一致性校验），或接受"模型可 steer 平台子会话"的行为变化 |
| 冷恢复还原 maxTokens | 上游明确拒绝（per-activation knobs 不进 descriptor） | 放弃；恢复后走路由默认值 |
| `agent-platform/batches` 事件 | 未注册；读路径拒绝未注册且非 `ignorable` 的事件 | 保留 dsh-session 补丁（锚点 `'agent-preset/selected',` 在 `known-event-types.js:22` 与 `lib/index.js:80` 仍唯一）；正规做法是 `plugin:` 前缀 + `appendPluginRecord`，但存量日志仍需旧类型名 |
| web-app 插件挂载 | `cordis.patch.yml` 仍在、仍用 `- insert:`，但 0.2.1 新增了 `presets/*.patch.yml` 链 | 追加位置需按新的 patch 链末端确认（未查证） |
| 补丁测试 | `test-agent-platform-runtime-patch.mjs` 有 30 余条 `assert.match` 全部锚定 0.1.1 源码/类型 | 保留的两项（`agent-platform/batches`、plugin 挂载）可留，其余按新补丁面重写；同时补 0.2 的 fail-closed 版本断言 |

迁移完成后官方 `deepseek-flash` / `deepseek-v4-pro` 目录由 0.2 runtime 直接提供；[早期模型目录补丁](2026-08-28-official-deepseek-model-catalog.md) 不再包含在构建补丁中。

## Alternatives considered

- **直接换 pin 再修到能构建**：即"边跑边修"。风险是把 Agent Platform、Workbench、会话互通一起打坏，且这些功能只能真机点验，半成品形态会污染用户的日常使用。分阶段迁移可以在任一阶段停下并保持可用。
- **升到 0.2.x 但砍掉自研插件**（丢掉 Agent Platform / Workbench / 会话互通换取协议同步）：等于功能倒退，用户明确要的是"官方新能力接进来"，不是砍功能。
- **留在 0.1.1 什么都不做**：官方最新模型与图片能力只能靠每个部署手写 `settings.yaml`，且拿不到 0.2.x 的图片 token 计费与 cache 标记；这正是不选它的原因（已用最小补丁缓解）。
- **用 headless CLI 或 ACP（`dsh-acp`）替代 Host RPC**：会绕开现在这套持久会话 / 项目 / 工作区模型，等于重做 app 的数据层，代价更大。

## Consequences

- 原生客户端与内置 Host 现在使用同一套 0.2 token、unary、remote-mux 和 projection 语义；旧点号 API 不再保留兼容分支。
- 旧会话数据保留，但升级由用户确认后触发并会改写磁盘格式。升级后的会话不应再交给 0.1.x 客户端打开。
- Agent Platform 的 DSH 子代理使用 0.2 activation 返回的 message id，不再伪造预分配 inbox id。若进程在 activation 已落盘但响应尚未持久化之间崩溃，重启后的批次可能无法证明原 message id，必须 fail closed。
- 0.2 不再提供 Agent Preset 写作者 API；原生预设界面保留只读 roster/read/select，复制、删除和打开预设目录功能禁用。
- 后台任务列表使用 `job/list` 的 whole-snapshot `rows` 流；单 job 输出追踪仍由现有工具卡和 durable `tool/*` 事件承载。
- 0.2.1 仍是 RC，版本文件、package 断言和 patch fixture 都会 fail closed，避免静默运行在未迁移的协议版本。
