# Agent Note: 语音派活 —— 唤醒词任务进独立后台会话

Status: implemented — 唤醒说的任务不再落进当前打开的对话

## Problem

唤醒词定稿后走的是 composer 的通用提交路径：文字进当前对话并发送。
App 启动默认停在一个空白新对话上，于是"唤醒 + 说任务"总是在碰巧打开的
会话/工作区里执行——用户无法用语音把活派到别处，也无法在不打断当前
工作的情况下开一个后台任务。

## Decision

- 唤醒定稿（且"唤醒自动发送"开启）→ `dispatchVoiceTask`：
  1. **工作区判定 v1（本地）**：任务文本里出现某个已引入工作区的名字
     （不区分大小写包含匹配）→ 派到该工作区；否则当前工作区。
  2. 在判定的 cwd 创建**独立新会话**（沿用当前 preset/模型/推理档），
     注入任务文本，后台运行 —— **不切换界面、不占用输入框**（听写期间
     流入输入框的实时文字在派发时恢复原状）。
  3. 完成提醒：拦截派发会话的 `turn/end` mux 事件（非当前会话的事件本来
     被丢弃）→ 系统通知 + Dock 角标；审批/提问本就有全局通知帧，无需
     另做。派发失败也发通知。
- 手动点麦克风的听写行为不变（只填输入框）；"唤醒自动发送"关掉时，
  唤醒听写也退回只填入。取消类指令仍整段放弃。

## Alternatives considered

- **单独调一次 LLM 判定工作区**：会加秒级延迟且要多养一条轻量路由。
  实际采用"执行者自判"：派发的任务附带文件夹清单（名字+绝对路径），
  执行任务的模型自己决定去哪个目录干活——判定与执行合一，零额外调用。
  局限：会话的名义 cwd 仍按第一级判定落位（侧栏分组按它算）。
- **唤醒任务仍进当前会话、只在空白会话时新建**：行为取决于"碰巧开着
  什么"，正是本次要修的不可预测性。
- **派发后自动切换到新会话**：与"静默执行"矛盾——用户唤醒派活的场景
  就是不想中断眼前的事。

## Consequences

- 唤醒 = 派活的心智模型成立：说话 → 通知到达 → 从会话列表打开结果。
- 派发会话与普通会话在列表中无差别显示（按工作区分组、running 呼吸点）。
- 完成通知点击只激活 App（NativeAlerts 现状），未深链到具体会话——
  后续可带 sessionId 直达。
