# Agent Note: 模型开子会话前，在对话里用卡片提示用户

Status: implemented — 模型开子会话前先在对话里出现卡片，确认后才创建；真实 Host 上已实测，App 里的点击路径还没有确认

## Problem

模型调用 `subagent` 或 `subagent_fork` 时，子会话立刻就开了，用户没有机会决定，对话里也只有一行普通工具记录：看不出这是子会话，看不出还在运行，也不能点进去。用户要求：模型想开子会话时先在对话里提示，用户确认后才开，卡片样式和普通会话一致。

dsh 没有规定模型什么时候开子会话：工具说明只建议把独立任务交出去以节省上下文，要求相互独立的任务一起开，全凭模型判断，也不要求询问用户。

## Decision

**Runtime（内置 dsh 补丁）**：`macos/Runtime-extras/dsh-tool-child-session-guard` 监听 `tools/pre-execute`，只拦 `subagent` 和 `subagent_fork`，通过 `ctx.approval.request` 询问，请求里带模型写的 description 和任务文本。`scripts/patch-agent-platform-runtime.mjs` 用锚点注入，锚点不存在时构建失败，不会静默失效。

这里直接调用 `approval.request`，而不是返回 `{ kind: "ask" }`：后者被拒绝时模型收到的是 “the user rejected tool”，读起来像可以重试。现在拒绝时模型收到「用户选择在当前会话完成，不要再开子会话。」。

- 审批策略是 `never`（完全访问）时不询问，直接放行：这个策略下 `ask` 会被拒绝，子会话就开不了了。
- `send_message`、`interrupt_agent`、`list_agents` 不拦，它们不会新开会话。

**App**：这两个工具的审批不进 `ApprovalSheet`，改为在对话里该工具调用的位置显示 `ChildSessionPromptCard`，系统通知保留。三种状态：

1. 等确认：标题「新会话：<description>」，一行说明，按钮「新建会话」和「在这里做」。
2. 运行中：普通会话行样式，标题加时间，行底显示运行线，可以点进去。
3. 已结束：普通会话行样式，「已完成 · 时间」，可以点进去。

「新建会话」回复 `allowed-once`，「在这里做」回复 `rejected`。不提供「总是允许」。

**不重复确认**：「新建」入口发出委派时记下任务文本，收到文本完全一致的审批就自动同意一次，用完即清。

**负责人会话**：`ds-agent --allow-child-sessions` 只对这次任务的会话、只对这两个工具自动同意。外部客户端要用 `/connect?token=…&interactions=answer` 换到能回答审批的 cookie。授权只在进程存活时有效，所以 `--attach` 也接受这个参数，`deepseek-collab` 的派工命令和自动续跑脚本都带上了它。

## Alternatives considered

- **只靠系统提示词要求模型先问用户**：软约束，模型可能不遵守，也没有真正拦住工具调用。
- **把 `subagent` 工具整个去掉，只保留手动入口**：用户明确要保留模型发起，只是要确认。
- **继续用现有的审批弹窗**：用户要的是对话里的卡片，弹窗打断阅读，而且看不到后续状态。
- **复用普通工具行，只加运行线**：用户否决，要卡片，样式和普通会话一致。
- **插件返回 `{ kind: "ask" }`**：写法更短，但拒绝文本不能改，模型会把它读成可以重试。
- **`--attach` 不带授权**：负责人断线恢复后再开子会话，会一直等一张没人点的卡片。

## Consequences

真实 Host（内置 runtime `0.2.1-rc.2`）上的实测，2026-11-02：

| 场景 | 结果 |
| --- | --- |
| 确认之前 | 模型调用后约 2 秒出现询问；等待 12 秒期间，子会话目录为空，会话总数不变 |
| 同意 | 子会话开始运行，模型继续 |
| 拒绝 | 不创建子会话，模型收到提示后在当前会话回复 |
| 一次开两个 | 第一个同意、第二个拒绝，只创建第一个，没有串 |
| 完全访问 | 不询问，子会话正常创建 |
| `--allow-child-sessions` | 询问后 1 毫秒内放行 |
| 进程退出后 `--attach` 接回 | 询问在第 11.12 秒出现，当场放行，回合正常结束 |

- **一次开多个时是逐张询问**，不是同时出现：dsh 串行执行工具的前置检查，第二次调用要等第一次回答后才开始。原来的验收标准写的是「出现两张卡片」，实际是一张答完出现下一张。
- 同一个 App 和脚本可以同时回答审批，先到的生效。测试中有一次两张卡片都不是脚本回答的，当时屏幕已解锁，推测是用户在 App 里点的，尚未确认。
- **还没有验证的**：在 App 里点卡片的完整路径；「新建」入口不重复确认（只有任务文本匹配的单测）；运行中切到别的会话再切回来，卡片是否还在。
- 补丁绑定 runtime 版本。npm 上 dsh 最新是 `0.2.1-rc.5`，固定版本是 `rc.2`，`build-macos-app.sh` 默认会拒绝构建；本地用 `DSH_RUNTIME_VERIFY_LATEST=0` 跳过这项检查。正式发版前要决定升级固定版本，或者改这项检查。
- 拒绝以后模型的行为仍由模型决定；实测中它都遵守了提示，没有重试。
