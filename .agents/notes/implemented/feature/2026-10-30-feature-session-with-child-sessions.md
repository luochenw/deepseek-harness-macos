# Agent Note: 一个功能一个主会话，取证、修复、审查作为它的子会话

Status: implemented — 侧边栏归拢、「新建」入口和一个功能一个主会话已落地；客户端直接创建子会话没有做

## Problem

现在做一个功能要开好几个会话：取证一个、修复一个、独立审查一个，返工有时再开一个（2026-10-29 的展开卡死修复用了 4 个顶层会话）。带来两个问题：

1. **侧边栏散乱**：这些会话都是同一个功能，却在侧边栏里各占一行，看不出它们属于同一件事。
2. **每轮从头熟悉**：每开一个新会话，DeepSeek 都要重新读规则、读代码、摸清来龙去脉，这是 2026-10-29 用户抱怨「一个需求做 2 个小时」的主要原因之一。

用户的问题：一个会话下面能不能有子会话，并且由主会话直接发起；dsh 能不能理解这种关系。

## dsh 已有的能力（读内置 runtime `0.2.1-rc.2` 的包和 Host 实际数据核实）

- **子会话是 dsh 的原生概念**（`dsh-subagent`）。本地 spawn 和 fork 出来的子级是**持久会话**：结束后还能继续发消息、可以中途引导、可以中断、可以冷恢复；子级完成后会自动把结果回报给主会话。
- **App 内置的标准预设已经启用了全部工具**（`dsh-web-app/presets/standard.patch.yml`）：
  - `subagent`：开一个全新的子会话，不带主会话的对话；
  - `subagent_fork`：开一个继承主会话已完成对话的子会话；
  - `send_message`：给子会话发消息；
  - `interrupt_agent`：中断子会话；
  - `list_agents`：列出子会话。
- **每个子会话可以单独指定模型和推理强度**（`modelSelectionSettings: true`），也可以有自己的工作目录。
- **默认限制**：最多 8 个子会话同时在线（`maxActiveSubagents`）；深度 1，也就是子会话不能再开孙会话（`subagent.maxDepth`）。
- **已经在用**：Host 上 243 个会话里，有 9 个带 `parentSessionId`，其中 6 个的 `origin` 是 `subagent`。例如 `session-f2014780` 在 10-28 开过 3 个子会话。
- **App 已有子会话界面**（`Subagents/`）：子会话目录、子会话对话、继续发消息（`subagents/prompt`）、中断（`subagents/interruptByParent`）。
- **限制**：客户端（App、`scripts/ds-agent`）**不能直接创建子会话**。`session/create` 只有 `workspaceId`、`cwd`、`sessionId`、`agentPreset` 四个参数，没有父会话；Host 给客户端的子会话接口只有 `subagents/prompt` 和 `subagents/interruptByParent`。子会话只能由主会话的模型调用工具来创建。
- **App 的缺口**：`sessionGroups`（`main.swift`）从 2026-08 起就按 `origin != "subagent"` 把子会话过滤掉了，所以子会话在侧边栏里完全看不到，只能从主会话右侧的子代理卡片进入。用户看到的「一个功能好几行」，来自 Claude 每轮新开一个顶层会话，不是子会话。

## Decision

分四步做，前三步不改 runtime，第 4 步暂不做：

1. **侧边栏把子会话收到主会话下面**（App，`Sidebar/` 和 `Sessions/`）。带 `parentSessionId` 的会话不在顶层显示，而是收在主会话下面，显示一个可展开的数量；子会话正在运行时，主会话那一行也显示运行线；点开子会话进入它的对话（复用现有子会话视图）。主会话不在列表里（比如被归档）时，子会话退回顶层显示，不能凭空消失。
2. **主会话里「新建子会话」入口**（App）。用户在主会话里输入任务，App 把一条固定格式的委派指令发给主会话：用 `subagent` 工具开一个子会话，把任务原样交给它，自己不做。现在在主会话里直接说「开一个子 agent 做 X」也能实现，这一步只是把它做成一个固定入口。
3. **协作方式改成一个功能一个主会话**（Claude 这边，`deepseek-collab` skill 和 brief 模板，不改 App 代码）。每个功能只开一个 DeepSeek 主会话当负责人，Claude 只给它发 brief：
   - 取证、修复各开一个子会话；
   - 返工发给原来那个修复子会话，它保留上下文，不用重新熟悉；
   - 独立审查开一个全新的子会话，不带主会话的对话，保证审查不受实现思路影响。
4. **（可选，以后做）客户端直接创建子会话**。给内置 runtime 加一个小 Host 插件，提供 `subagents/start` 接口，内部调用 `ctx.subagents.startActivation()`，这样「新建子会话」不经过模型转述。只有第 2 步的转述被证明不可靠时才做。

## Alternatives considered

- **App 自己在本地记会话分组，不靠 dsh**：dsh 已经有父子关系和子会话目录，再造一套会出现两套真相，换设备或重装就丢。
- **用 dsh 实验性的 Agent Team**（`dsh-experimental-agent-team`：Lead、具名队员、互发消息、共享任务板）：能力更强，但还是实验功能，标准预设没有启用，要改 runtime 配置，App 也没有对应界面。先用稳定的子会话；Agent Team 稳定以后再评估。
- **继续每轮开新的顶层会话，只在侧边栏按标题前缀归组**：能让侧边栏整齐，但解决不了每轮重新熟悉上下文的效率问题。
- **直接做第 4 步（runtime 插件）**：要长期维护一个上游没有的 runtime 补丁，每次升级 runtime 都要跟着适配。在模型转述够用的情况下不值得。

## Consequences

- 侧边栏归拢和父行运行线由 `macos/DSHTests/DSHSidebarTests.swift` 覆盖，「新建」的委派文本由单测覆盖。
- 模型会不会原样转交任务文本，取决于模型；「新建」入口靠文本完全一致来免去二次确认，模型改写以后会出现一张卡片，而不是直接放行。这条在真实 App 里还没有走过。
- `deepseek-collab` 已改成一个功能一个负责人。「主会话 → 取证 → 修复 → 全新审查 → 返工」的完整流程还没有用真实功能走一遍并记录总耗时。
- 模型发起子会话现在要先确认，见 [提示卡片](2026-10-30-child-session-prompt-card.md)。负责人会话要带 `--allow-child-sessions`，否则会停在卡片上。
- 深度只有 1：如果主会话本身就是别人的子会话，它就不能再开子会话。主会话必须是顶层会话。
- 子会话和主会话共用工作目录和权限，并行的两个子会话改同一批文件会互相覆盖。仍然要按功能域分工，同一时间每个域只有一个写代码的子会话。
- 子会话的结果会回报进主会话，主会话的上下文会越来越长；长功能可能需要在中途开新的主会话。
- 第 2 步依赖模型转述指令，可能改写任务文本。委派指令要求原样转交，验收时核对子会话的第一条消息。
